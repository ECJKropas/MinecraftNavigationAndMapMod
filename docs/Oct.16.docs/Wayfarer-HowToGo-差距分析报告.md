# Wayfarer 与竞品 HowToGo 全方位差距分析报告

> **对比对象**：Wayfarer 0.4.1（`/Users/cjkim/Documents/MinecraftNavigationAndMapMod`） vs HowToGo 0.2.1-pre1（`~/github_pro/howtogo`，来源 `https://github.com/Dong-awa/howtogo`）
> **版本 / 日期**：v1.0 ｜ 2026-10-06
> **证据范围**：两仓库的源码、构建脚本与仓库内文档（不使用网络二手信息）

**核心发现**：HowToGo 在"成品化导航体验 + 自动化回归工程"两项上领先 Wayfarer 一个代际；Wayfarer 在多版本覆盖、网页路网编辑器、CI 与工程文档体系上保有结构性优势。追赶的正确姿势是补齐导航闭环与工程基建，而不是重写。

> 本章所有事实均来自两个仓库的源码、构建脚本与仓库内文档；标注 `未实测`/`未检索到` 的条目为当前证据不足以断言的项，不作推断性结论。

# 第 2 章 功能与产品能力对比

> 证据来源：`howtogo/README.md`（功能与配置章节）、`howtogo/src/**`（road / route / transit / client / compat 包）、`howtogo/CHANGELOG.md`；Wayfarer `src/main` 与 `src/main/resources`（检索范围见 §1.2 证据规则）。

## 2.1 路网数据模型与编辑

| 能力项 | Wayfarer | HowToGo |
|---|---|---|
| 数据获取方式 | 轨迹录制（SurveySession）：边走边采集，可批量生成路网 | 游戏内标记：直接对道路打点/连线 |
| 编辑入口 | 内置网页编辑器（HttpServer + Leaflet），键鼠大屏操作、几何可视化 | 游戏内交互为主（玩家在当前视角内操作） |
| 道路属性 | 路段分类（G/S/Y/X/C 等类目）、节点/路段拓扑 | 道路等级、层（立交/隧道分层）、单行道语义、道路类型 |
| 批量能力 | 支持对已采集轨迹做整体处理与网页端编辑 | 未在源码中检索到批量导入工具；以逐条标注为主 |
| 校验与约束 | 依赖人工检查与几何显示 | 有独立的连通性/单行道/路径抽稀检查类（见 §4.1） |

**分析**：这一组能力上 Wayfarer 并不落后，甚至在"编辑效率"上更强——网页编辑器配合 Leaflet 可视化，能做的事（批量整理、几何修正、跨屏扫视）在游戏内 UI 里做不到。HowToGo 的优势在于"属性语义更细"：道路等级、层、单行道是寻路质量的前置条件，而 Wayfarer 当前的路网属性主要服务于"画出来"，尚未充分服务于"算出来"。

## 2.2 寻路与导航方式

| 能力项 | Wayfarer | HowToGo |
|---|---|---|
| 寻路算法 | Dijkstra（单源最短路） | A\*，支持多源多目标、候选起点/终点 |
| 出行方式 | 单一陆地方式为主 | 步行 / 驾车 / 公共交通三种方式 |
| 时间估算 | 未实测；未见按道路等级修正的计时模型 | 有驾车计时修正模型，ETA 参与路线比较 |
| 偏航处理 | 未在源码中检索到按道路等级区分的偏航容差策略 | 偏航容差按道路等级设定 |
| 起终点吸附 | LocationSnapper 对路网节点做线性遍历吸附 | 由网格空间索引（RoadSpatialIndex）加速候选点查询 |
| 导航反馈 | 基础 HUD 指示 | 逐段指引 + 播报（见 §2.3） |

**分析**：这是本次对比中最实的一段差距，且不是"有没有"的问题，而是"算不算得对、算得快不快"的问题——三者叠加（无索引 → 大路网变慢；无方式区分 → 步行路线混入车道；无计时修正 → ETA 不可信）会让导航结果在真实使用时频繁不可信。差距定级：**P0**。

## 2.3 目的地 / POI 与语音交互

| 能力项 | Wayfarer | HowToGo |
|---|---|---|
| 目的地选择 | 以路网节点/位置为主 | 支持 POI 体系：关键词搜索、最近 POI |
| 语义搜索 | 未在源码中检索到 | 有（POI 关键词检索） |
| 语音/播报 | 未在源码中检索到 TTS/播报实现 | 有 Narration 相关实现与专门检查类（NarrationCheck） |
| 命令入口 | 有基础指令支持（未逐条核对覆盖面） | 有配置与指令体系，支持 AUTO 自检 |

**分析**：Wayfarer 缺的是"导航的消费侧入口"。用户能画出一张漂亮的路网，但要开始一次导航，必须自己在地图上找到并点选目标；HowToGo 允许"搜个地点就去"。语音播报在长途行进中影响更大，因为玩家开车/跑图时不方便看 HUD。定级：POI 与目的地搜索 **P1（偏高）**，语音播报 **P1（偏低）**。

## 2.4 外部交运与模组集成

| 能力项 | Wayfarer | HowToGo |
|---|---|---|
| 地图模组 | Xaero's World Map 叠加渲染 | Xaero（渲染扩展点，无 mixin） |
| 交通类模组 | 未在源码中检索到 Create / MTR 集成 | 反射只读集成 Create（列车）、MTR（地铁，联机近窗口范围） |
| 其他模组 | 未在源码中检索到 | MCphone、Xaero 小地图 waypoint |
| 公共交通 | 未在源码中检索到公交线路模型 | 公交线路 + 到站指引 + 专门检查类（TransitGuidanceCheck、MtrImportCheck） |
| 集成技术手段 | mixin + 直接依赖（malilib） | 反射调用，编译期 `compileOnly`，运行期缺失即降级 |

**分析**：HowToGo 的集成策略是"广撒网 + 不硬绑定"：反射调用使它在目标模组缺失时仍能启动，代价是不同版本下需要维护反射签名。Wayfarer 当前不走这条路。此项对用户价值高但**依赖外部生态规模**，定级 **P2**（不建议在 Q4 投入）。

## 2.5 地图与 HUD 呈现

| 能力项 | Wayfarer | HowToGo |
|---|---|---|
| 地图渲染 | Xaero 叠加层绘制路网 | Xaero 扩展点渲染 + 自有面板，含标签缓存（LabelCacheCheck） |
| 独立地图视图 | 有：内置 Web 地图（Leaflet），可脱离游戏打开 | 未在源码中检索到 Web 视图 |
| 显示过滤 | 基础 | 有显示过滤与标签缓存机制 |
| 网页编辑联动 | 有：网页端编辑直接改路网数据 | 无 Web 端 |

**分析**：Wayfarer 在"地图作为可编辑资产"这一层是领先的——网页地图既是编辑工具，也是路网的对外呈现方式（可截图、可分享、可在双屏环境使用）。HowToGo 把渲染做在游戏内，路径是"沉浸"；Wayfarer 走的是"外置工作台"路径。**这是差异化资产，不是要被补平的差距。**

## 2.6 闭环诊断与优先补齐建议

把使用链路拆成四段逐段判定：

| 链路环节 | Wayfarer 状态 | HowToGo 状态 | 判定 |
|---|---|---|---|
| ① 采集（走路生成路网） | 成熟（SurveySession 轨迹录制） | 有（游戏内标记） | 打平，Wayfarer 更省力 |
| ② 编辑（整理与修正） | 成熟（网页编辑器 + 可视化） | 弱（游戏内逐条操作） | **Wayfarer 领先** |
| ③ 导航（规划与引导） | 半成品（单方式、无索引、无 ETA 修正） | 成熟（多方式、索引、计时修正） | **落后，P0** |
| ④ 反馈（到达、播报、纠偏） | 基本缺失 | 成熟（播报、偏航容差、到站指引） | **落后，P1** |

**若只允许先补 3 项功能，建议顺序为**：

1. **路网空间索引 + 面向真实使用的路径规划体验**（多方式区分、计时修正）——直接决定"导航能不能用"，且是后续 POI、语音等所有下游能力的公共地基。
2. **POI / 目的地搜索与"最近 POI"**——把已有路网资产变成可被消费的目的地库，补齐导航入口。
3. **行进播报（TTS 或文字播报）**——单次改动小、在长距离行进中体感提升最明显。

**边界提示**：本节只做"补哪三项"的取舍判断，具体的任务拆解、落点模块与验收标准见配套文档《Wayfarer 追赶与改进计划》第 2 章。
# 第 3 章 架构、技术栈与性能对比

## 3.1 模块划分与可移植性

| 对比项 | Wayfarer | HowToGo |
|---|---|---|
| 源码组织 | 单套源码 + ReplayMod Preprocessor 多版本覆盖：`versions/<mc>/src` 只放差异，`common.gradle.kts` 被各版本子项目共用 | 双源集：`src.common`（纯 Java 的路网 / 路由 / transit 逻辑，不含 MC 依赖）+ `src.main`（加载器、客户端、兼容层） |
| 版本支持 | 3 个：1.20.1、26.1.1、26.2（`settings.json`） | 1 个：1.21.1 |
| 核心逻辑能否脱离游戏运行 | 依赖 MC 类型与客户端上下文（包结构 `client/road|nav|render|gui` 与 MC API 同级） | `src.common` 可独立运行，这正是无头回归工具（`tools/routing-harness`）能存在的前提 |
| 移植成本 | 新 MC 版本 = 在 `versions/<新版本>/src` 补差异 + Preprocessor 指令 | 新 MC 版本 = 重写 `src.main` 加载器层，核心逻辑层不动；新加载器同理 |
| 单点验证效率 | 低：逻辑改动必须在客户端内验证，无自动化入口 | 高：路网/路由缺陷可在无游戏环境下复现与断言 |

**根因分析**：差异不是技术偏好，而是**优先级不同的必然结果**。Wayfarer 把"一套代码覆盖 3 个 MC 版本 + 3 个发行渠道"放在第一位，因此选择 Preprocessor 路线，逻辑层必须与 MC 类型共存；HowToGo 把"核心逻辑可测试、可迁移"放在第一位，因此抽出无 MC 依赖的 `src.common`，用单版本换取验证效率。

**定级 P1**：不要求 Wayfarer 放弃多版本，而是**抽出"路网 + 路由 + 数据编解码"这一层与 MC 无关的纯逻辑**（实现路径见改造计划第 3 章），这样既保住多版本优势，又拿回可测试性。

## 3.2 依赖与集成方式

| 对比项 | Wayfarer | HowToGo |
|---|---|---|
| MC 侧注入手段 | mixin（`wayfarer.mixins.json`）+ Fabric API | 无 mixin 注入 Xaero：走其公开渲染扩展点 |
| 必需前置依赖 | malilib（硬依赖，缺失无法运行） | Xaero's World Map（声明为硬依赖） |
| 可选集成 | 未检索到专门的 compat 集成模块（源码中 create/mtr 关键词均为方法名，非模组集成） | 反射只读集成 Create、MTR、MCphone、Xaero 小地图 waypoint；目标模组缺失时降级而非崩溃 |
| 闭源依赖处理 | `ref/` 下 jar + `.gitignore` 排除，克隆后需自行补齐才能编译 | `libs/` 下 jar 仅 `compileOnly`，不打包分发 |
| 升级适配成本 | 高：Xaero / malilib / MC API 三者任一变更都可能触碰 mixin 与调用点 | 中：反射签名需按目标模组版本核对，但失败即降级，不阻塞启动 |

**分析**：HowToGo 的"反射 + compileOnly + 降级"是一套经过取舍的工程策略——用运行期的不确定性换取编译期的宽松与分发的干净（不打包他人 jar，规避再分发许可问题）。Wayfarer 的 mixin 路线控制力更强、实现也更彻底，但把"必须跟着上游版本跑"的负担固化进了架构。**定级 P2**（不值得在本轮改造中推倒重来，但新写的集成点应优先选扩展点/反射而非 mixin）。

## 3.3 寻路算法与查询性能

| 对比项 | Wayfarer | HowToGo |
|---|---|---|
| 空间检索 | `LocationSnapper` 对路网节点做线性遍历吸附 | `RoadSpatialIndex`（网格空间索引）作为精确加速器 |
| 吸附查询复杂度 | O(N)（N = 路网节点数） | 源码可推断为按网格定位邻近格子，复杂度与网格局部密度相关，非全量扫描 |
| 寻路算法 | Dijkstra（`Router`） | A\*，支持多源多目标与候选起点/终点集合 |
| 启发式 | 未检索到启发式估价函数 | 有（A\* 方向引导） |
| 结果修正 | 未检索到按道路等级修正的通行时间模型 | 驾车计时修正；偏航容差按道路等级 |
| 缓存与复用 | 未检索到路由工作区复用机制 | 有路由工作区复用与标签缓存（配套 `LabelCacheCheck` 检查） |
| 实测数据 | 未实测（N/A） | 未实测（N/A）——两仓库均未提供基准测试数据 |

**性能结论（区分证据强度）**：
