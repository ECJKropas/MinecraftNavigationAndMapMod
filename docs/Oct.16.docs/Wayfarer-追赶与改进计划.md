# Wayfarer 追赶与改进计划（2026 Q4 – 2027 Q1）

> **依据**：《Wayfarer 与竞品 HowToGo 全方位差距分析报告》的 12 项差距清单与 Top 5 结论
> **周期**：2026-10-06 → 2027-01-10（14 周，4 个里程碑）｜ **形式**：单人开发
> **一句话目标**：把 Wayfarer 从"可编辑路网的工具"推进到"作者本人可日常跟着走的导航模组"，同时不牺牲多版本覆盖与网页编辑器两项差异化优势。

---

# 第 1 章 计划概览与量化目标

## 1.1 计划定位与三条主线

本计划是《Wayfarer 与竞品 HowToGo 全方位差距分析报告》配套的执行方案，起点 2026-10-06，终点 2027-01-10（14 周），面向单人开发场景，按"能在真实游戏中用起来"而非"功能对齐竞品"评价成败。

三条主线及其关系：

1. **工程基建先行**：先建立可回归验证的能力（无头检查器 + 性能基线）与数据加速结构（空间索引），让后续每一步改动都可度量、可回退。
2. **导航闭环补齐**：在基建之上补齐"规划—引导—纠偏"链路（A\* 化、出行方式区分、ETA、偏航重规划），把已有的路网资产变成可消费的导航能力。
3. **差异化强化**：把多版本覆盖与网页编辑器这两个竞品空白项做成对外叙事，而不是在追赶中被稀释。

## 1.2 量化目标（北极星与 KPI）

> 口径说明：`当前值` 为 `未实测（N/A）` 的项，均需在 M1 内建立基线后方可评估；目标值为本计划设定的工程目标，非现状描述。性能阈值对应"典型单人路网"规模假设（节点数 5 万–10 万量级，该假设需在 M1 用真实存档数据校正）。

| 指标 | 当前值 | 目标值（M4 验收） | 度量口径 | 数据来源 |
|---|---|---|---|---|
| **北极星**：一次完整跨区域导航 | 未达成（导航为半成品） | 不打开网页编辑器，游戏内完成一次 ≥500 格距离的导航，全程无需人工干预寻路 | 手动场景验收（固定测试路线） | 实测记录 |
| KPI-1 吸附/邻近查询耗时 | 未实测（N/A） | 5 万节点路网下 P95 ≤ 5 ms | 单次吸附查询耗时分布（harness 内计时） | harness 输出 |
| KPI-2 路径规划耗时 | 未实测（N/A） | 5 万节点、平均距离 800 格下 P95 ≤ 80 ms | 单次规划耗时分布 | harness 输出 |
| KPI-3 寻路扩展规模 | 未实测（N/A） | 相对 M1 基线，扩展节点数下降 ≥ 50% | 同一组路线在改造前后的扩展节点数对比 | harness 输出 |
| KPI-4 无头检查覆盖 | 0 条 | ≥ 12 条，覆盖连通性、单行道/方向、索引、路径抽稀四类 | 检查项数量与失败样本可复现率 | harness 仓库 |
| KPI-5 路网相关异常 | 未实测（N/A） | 连续 3 小时实测游玩，无路网相关异常堆栈 | 客户端日志扫描 | 实测日志 |
| KPI-6 发布节奏 | — | Q4 内产出 ≥ 2 个可分发版本（v0.5.0 与 v0.5.x），覆盖 3 个 MC 版本 | GitHub/Modrinth 发布记录 | 发布产物 |
| KPI-7 变更可追溯 | 无顶层 CHANGELOG | 每个版本 100% 覆盖改动与改动原因 | CHANGELOG 条目数 / 版本改动数 | 仓库文件 |

## 1.3 范围边界与"明确不做"

**范围内**：路网空间索引、寻路算法与出行方式、ETA 与偏航处理、POI 与目的地搜索、导航播报、无头检查器、性能基线、配置整理、变更文档。

**明确不做**（见第 5 章理由）：

| 不做事项 | 理由 |
|---|---|
| 整体重写或架构推倒重来 | 数据/编辑/构建/文档均为有效资产，差距属增量可补范围 |
| 许可从 GPL-3.0 迁移为 MIT | 与本项目定位冲突、合规成本高，且非用户可感知能力 |
| 在 Q4 引入 Create / MTR 反射集成 | 定级 P2，依赖外部生态版本稳定，投入产出比低 |
| 彻底移除 mixin、改用纯扩展点 | 改造面过广，仅要求"新增集成点优先选反射/扩展点" |
| 引入任何新的闭源必需依赖 | 克隆后不可开箱编译的痛点已存在，不再加重 |
| NeoForge 等新加载器移植 | 与"多版本覆盖"主线冲突，收益不明 |

# 第 3 章 工程基建方案

> 本章 4 项基建是 P0 任务的实现路径说明，目标是让"改一处不再悄悄坏另一处"，并让性能提升可被度量。

## 3.1 无头回归检查器（harness）

**目标**：在不启动 Minecraft 的前提下，用可控输入复现并断言路网/路由缺陷，把"线上问题"转化为"可重跑的检查项"。

**关键设计**：

| 设计点 | 方案 |
|---|---|
| 输入 | 结构化的路网数据（由存档导出或手工构造的最小样本），避免依赖游戏运行时 |
| 输出 | 结构化结果（检查项 × 通过/失败 × 上下文）+ 明确退出码，便于 CI 判定 |
| 运行方式 | 独立 Gradle 任务（示例：`./gradlew checkNetwork`）+ CI 中独立 job；不依赖游戏、不需图形环境 |
| 检查项组织 | 一个检查类对应一类缺陷，失败时打印可复现描述（类似竞品 `Harness` + 各 `XxxCheck` 的组织方式） |
| 数据固化 | 每个真实踩坑案例都固化为一个样本文件 + 一条检查，样本随代码入库 |

**首批 12 条检查项（验收目标 KPI-4）**：

| 类别 | 检查项 |
|---|---|
| 拓扑一致性 | ① 连通性 ② 孤立节点/孤岛 ③ 重复边与自环 |
| 吸附与索引 | ④ 索引结果与全量遍历逐点一致 ⑤ 吸附最近性（返回的确实是最近节点） |
| 寻路正确性 | ⑥ 路径可达性 ⑦ 路径代价单调性（子路径代价 ≤ 全路径） ⑧ 路径不穿越非连通段 |
| 数据完整性 | ⑨ 序列化往返一致（存后读回逐字段相等） ⑩ 按存档/维度隔离（不串档） |
| 交互与提示 | ⑪ 偏航判定边界（20 格阈值两侧不误判） ⑫ 转向提示序列与实际路线一致 |

**验收标准**：≥ 12 条检查可在无游戏环境运行；人为注入 3 类缺陷（断边、孤岛、索引失配）均能被对应检查捕获并给出定位信息。

## 3.2 性能度量与空间索引

**空间索引设计要点**：

| 项 | 方案 |
|---|---|
| 结构 | 均匀网格（cell 边长按典型路网密度选定，先取 64 格并实测调整），cell → 节点/路段 id 列表 |
| 接口 | `findNearest(pos, maxRadius)`、`searchWithin(bbox)`；**对外接口与现有 `LocationSnapper` 保持一致**，先替换内部实现，降低侵入 |
| 复杂度 | 由 O(N) 全量扫描降为与邻近 cell 内元素数量相关；边界情况（超大搜索半径）自动退化为逐格扩展直到命中 |
| 正确性保障 | 检查项 ④ 做"与全量遍历结果逐点一致"的等价断言，确保加速不改结果 |
| 一致性 | 路网增删改后必须同步更新索引；对写操作建立"脏标记 + 惰性重建"策略，避免每次编辑全量重建 |
| 内存 | 只存 id 与坐标引用，不复制几何数据 |

**度量方案**：harness 内建计时模块，输出 `baseline.json`，字段包含吸附查询耗时分布（P50/P95）、路径规划耗时分布、平均扩展节点数、路网规模（节点/路段数）。每次运行与基线对比，作为回归判据。

**回归门禁**：任一指标劣化超基线 20% 视为性能回归，CI 中阻断并输出对比明细。

## 3.3 逻辑层抽取（渐进式，不破坏多版本）

**目标**：让"路网模型 + 路由 + 索引 + 序列化"这部分不含 MC 类型的代码能被 harness 独立编译运行，同时 3 个 MC 版本构建保持通过。

**实施原则**：

1. **只抽纯逻辑，不做一次性大搬迁**——按模块逐个迁移，每迁完一个模块立刻在 harness 中补上对应检查项。
2. **用类型隔离代替重写**——MC 类型（坐标、方块位置）在边界处转换为纯数据结构（数值 + id），内部逻辑只依赖后者；通过适配器保持现有调用点不变。
3. **与 Preprocessor 共存**——纯逻辑部分天然不需要按版本条件编译，将其置于共用源集；版本差异仍由 `versions/<mc>/src` 承载。
4. **回退友好**——每步迁移独立可回退；若某模块抽取导致两个以上版本构建失败且 2 天内无法修复，立即回退该模块并保留其余成果。

**验收标准**：harness 在不加载 Minecraft 的进程中即可编译运行并通过全部检查项；1.20.1 / 26.1.1 / 26.2 三个版本的构建与构建矩阵 CI 全部通过。

## 3.4 构建与发布增强

| 项 | 方案 | 验收标准 |
|---|---|---|
| CI 扩展 | 在现有 build/gradle/matrix 工作流中新增"检查器 + 性能基线"job（无游戏、秒级） | PR/推送时自动跑，失败即阻断 |
| 性能报告 | 每次 CI 运行产出基线对比摘要，随构建产物归档 | 可回溯任意版本的三项性能指标 |
| 版本与变更 | 新建顶层 `CHANGELOG.md`，条目格式"改动 + 原因 + 影响面"；版本号遵循现有 0.5.x 序列 | 每个版本 100% 覆盖改动与原因 |
| README 增补 | 新增"已知限制"章节（诚实披露）与"最短上手路径"（≤ 5 步从安装到完成一次导航） | 新用户按文档可独立完成首次导航 |
| 发布链路 | 复用已有 `docs/auto_modrinth_upload.command`，发布前加检查清单（三版本构建通过、检查器全绿、CHANGELOG 已更新） | v0.5.0 发布一次性通过清单 |
| 构建前置说明 | README 明确 `ref/` 闭源 jar 的补齐方式与版本对应关系 | 消除"克隆后无法编译"的沟通成本 |
