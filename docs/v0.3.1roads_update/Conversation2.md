### 问题一：十字交叉路口的“自动节点生成”与“偏差吸附”

**解决方案（实时吸附与自动切分）**：

每当玩家**结束一段道路的录制**（或新增一个节点）时，模组在后台执行以下逻辑：

1. **交叉检测**：将新生成的这条路段（线段A），与已保存的所有旧路段（线段B）进行**二维平面相交检测**（忽略Y轴，用叉积法判断）。
2. **精度吸附（防偏差）**：

   - 遍历现有的 `Node` 列表，查找距离该交点 **2格以内** 的节点。
   - **如果有**：直接把新路段的端点坐标**修正**为这个已存在的节点ID（完美吸附，消除你担心的手抖偏差）。
   - **如果没有**：在交点处**自动创建一个新节点**，然后**自动将旧路段从中间切开**（旧路段变为两段，中间夹着新节点），并把新路段连接上这个新节点。
3. **性能优化**：只在“生成新路段时”触发检测，不要每Tick跑，纯客户端计算量完全可控。

这样一来，玩家不需要在十字路口按任何键，道路交汇处也会自动形成完美的拓扑节点。

### 问题二：如何区分“故意直角/锐角”与“需要平滑的曲线”

这是道路渲染中最头疼的问题。MC的方块世界天然存在大量90°直角弯，如果无差别套用Catmull-Rom样条，所有直角都会被“抹圆”，变成像赛道一样的弧线，丧失城市道路的方正感。

**解决方案：引入“节点拐角模式（Corner Mode）” + “转弯半径检测”**

不要把所有节点都输入样条生成器，而是给你的 `Node` 数据加一个字段：`cornerType`（枚举：`SHARP`/`ROUND`/`AUTO`）。

**关键是怎么自动判断 `SHARP` 还是 `ROUND`：**

不要在渲染时判断，要在**录制（生成节点）时判断**。利用玩家在短时间内移动的**空间距离**来推算：

- 当玩家转向时（Yaw角变化超过阈值），记录**转向开始点A**和**转向结束点B**。
- 计算从A到B的**直线距离（弦长）**。
- **判定逻辑（极其有效）**：
  - 如果 **弦长 ≤ 3个方块**（即玩家几乎是原地转了个90°），判定为 `SHARP`（直角/锐角）。渲染时，在这个节点**不启用样条插值**，直接强制画成尖锐的折线。
  - 如果 **弦长 > 6个方块**（玩家绕了一个大弯才转过来），判定为 `ROUND`（曲线弯道）。渲染时，启用样条插值，让弯道变得丝滑。

**渲染层的具体实现（最稳妥的做法）：**

不要将整条路的节点一股脑扔进样条。改为按 **“节点对”** 分段渲染：

1. 遍历路段的节点列表 `[P0, P1, P2, P3...]`。
2. 检查当前节点 `P1` 的 `cornerType`。
3. 如果 `P1` 是 `SHARP`：**断开连接**，`P0` 到 `P1` 画直线，`P1` 到 `P2` 画直线（呈现锋利拐角）。
4. 如果 `P1` 是 `ROUND`：将 `P0, P1, P2` 传入 Catmull-Rom 生成平滑弧线。

**额外补充（手动修正的退路）**：因为自动算法有时候会误判（比如高速冲直角弯），建议你再绑定一个快捷键（比如 `R`），在录制时按一下可以**强制切换当前拐角模式**。玩家看着屏幕上的路径点颜色（红色=锐角，蓝色=弧线），随时手动纠正，体验极佳。

### 一、最终数据模型（三层完全解耦）

为了同时支持导航（图论）和美观渲染（样条），数据分为三层，互不污染：

```json

    "n_001": { "x": 100, "z": 200, "y": 64, "cornerType": "AUTO" },
```

### 二、录制交互与状态机（玩家操作流）

| 按键 | 功能 |
| :--- | :--- |
| **`R`** | **开始/结束录制**。按下开始记录起点节点；再次按下结束录制，触发全局拓扑修正。 |
| **`G`** | **强制插入节点**。在当前位置强行打点（用于路口、匝道分合流，即使角度没变）。 |

4. `RECORDING` → 按 `R` → 记录终点节点，结束录制，**立即执行全局拓扑合并**（见下文第三节）。

### 三、自动修正十字路口 & 偏差吸附（核心算法）

解决你担心的“-50到50”与“0到5”在原点相交却不自知的问题。**只在录制结束时触发一次**，节省性能：

**算法流程（针对新生成的所有路段，与旧路段比对）**：
1. **遍历比对**：取新路段的每一段子线段（`[P_i, P_{i+1}]`），与所有旧路段的每一段子线段进行**二维叉积相交检测**（忽略Y轴）。
2. **计算精确交点**：若相交，算出数学交点坐标 `(x, z)`。
3. **节点吸附（去偏差）**：
   - 在现有全局 `nodes` 中查找离该交点 **2.5格以内** 的节点。
   - **若找到**：直接将新、旧线段在此处的端点坐标修正为那个已存在的 `NodeId`（消除手抖偏差）。
   - **若未找到**：创建一个新节点 `Node_new`，位置为交点坐标。
4. **拓扑切分（自动挂接）**：
   - 将包含此交点的**旧路段**从中间切断（一分为二），并把 `Node_new` 插入其中。
   - 将包含此交点的**新路段**从中间切断，也把 `Node_new` 插入其中。
   - 此时，两条路通过 `Node_new` 在拓扑图上**真正连通**，导航自动生效。

> 此算法等效于“在路网中埋入一个十字路口节点”，全程无需玩家按键。

### 四、直角/锐角 vs 曲线弯道 的精准识别（弦长检测）

区分“MC方正转角”和“自然曲线”的算法，在**自动记录节点**时执行：

- 维护一个临时缓冲区，存放玩家最近 **1.5秒** 内的坐标轨迹（约20个点）。
- 当触发角度变化（记录节点）时，取缓冲区的**第一个点A** 和 **最后一个点B**。
- 计算 **弦长** `d = A.distanceTo(B)`（即转向起点到转向终点的直线距离）。
- **判定逻辑（硬阈值）**：
  - 若 `d <= 2.5` 个方块（玩家近乎原地转身） → 判定为 **`SHARP`**（渲染时不启用样条，画尖锐折线）。
  - 若 `d >= 4.5` 个方块（玩家绕了大弯） → 判定为 **`ROUND`**（渲染时启用Catmull-Rom样条，生成平滑弧线）。
  - 介于中间 → 保留为 `AUTO`，交由玩家按 `T` 键手动修正。

### 五、渲染策略（分段绘制，直曲分离）

在 `WorldRenderEvents` 中绘制路网时，不要一股脑全样条，按节点类型分段渲染：

1. 遍历 `Segment` 的 `nodeIds` 列表 `[P0, P1, P2, P3, P4]`。
2. 逻辑：
   - 从 `P0` 开始，判断 `P1` 的 `cornerType`。
   - 若 `P1` 是 `SHARP`：**断开连接**，画直线 `P0 -> P1`，再画直线 `P1 -> P2`（呈现锋利拐角）。
   - 若 `P1` 是 `ROUND`：将 `P0, P1, P2` 三个点传入 Catmull-Rom 算法，生成20个插值点，画出平滑弧线。
3. **视觉反馈**：节点处用**小圆球**标记，`SHARP` 显示红色，`ROUND` 显示蓝色，方便玩家实时检查并随时按 `T` 纠正。

### 阶段零：修正数据模型（推翻之前的“RoadName”）

根据共识，**`RoadName` 不要了，升级为 `Road`（逻辑道路对象）**。

**你的具体任务：**
创建 3 个核心 POJO 类，别用 `String` 当ID，统一用 `UUID`。

1. **`Node`**：`UUID id`，`int x`，`int z`，`int y`（高度），`CornerType type`（枚举：SHARP/ROUND/AUTO）。
2. **`Segment`**：`UUID id`，`List<UUID> nodeIds`（**有序**，长度>=2），`UUID roadId`（指向所属道路）。
3. **`Road`**：`UUID id`，`String name`（可空），`List<UUID> segmentIds`，`String color`。

**关键编码细节**：`Segment` 本身**不再存** `roadNameId`，只存 `roadId`。`Road` 通过 `segmentIds` 集合反向管理所有路段。

### 阶段一：实现“移动分析器”（最核心的算法）

不要只检测角度（Yaw），按照共识，检测**运动向量（Velocity）变化** + **速度突变**。

**你的具体任务（写一个 `MovementAnalyzer` 类）：**

- 维护一个**长度为 20 的环形缓冲区**，存放过去 1 秒的 `Vec3d` 位置和当前时间戳。
- 每 Tick（`ClientTickEvent`）注入玩家位置。
- **判定逻辑（硬阈值，先写死）**：
  - **计算即时速度**：`当前位置 - 1秒前位置` 的长度。
  - **计算航向角**：`atan2(z变化量, x变化量)`（注意：这是**移动方向**，不是玩家的头朝向）。
  - **触发候选节点的条件（满足任意一条即触发）**：
    - **急转弯**：当前航向角与 0.5 秒前航向角的差值 > **25度**。
    - **停留/减速**：即时速度 < 0.1 m/s，且持续了 **1.5秒**（大概率在路口观察）。
    - **速度骤降**：当前速度比 1 秒前速度降低了 **60%** 以上（刹车准备拐弯）。

- **输出**：触发时，抛出一个 `CandidateNodeEvent`，包含当前精确坐标和 `confidence`（置信度，急转弯给0.7，停留给0.9）。

### 阶段二：实现“录制状态机”与“候选节点确认”

鉴于你是 Mapper（制图员），采用 **“自动候选 + 手动确认（G键）”** 的混合模式。

**你的具体任务：**

1. **R键**：切换 `IDLE`（空闲）和 `RECORDING`（录制中）状态。
2. **在 `RECORDING` 状态下**：
   - 后台运行阶段一的 `MovementAnalyzer`。
   - 如果分析器抛出了 `CandidateNodeEvent`：
     - **置信度 > 0.85**（如停留）：**自动确认**，直接将节点加入当前 `tempSegment` 的节点列表，并在屏幕中央弹出提示 `“已记录路口节点”`。
     - **置信度 0.6 ~ 0.85**（如急转弯）：在屏幕右上角显示一个**半透明的小图标（❓）**，但不录入。
3. **G键（强制插入）**：
   - 无论是否有提示，按下 G 键，**立刻**在玩家当前位置插入一个节点，并**强制结束**当前段，将新节点作为新段的起点。
   - 这解决了“系统没识别出匝道，但玩家肉眼看到了”的场景。

### 阶段三：实现“临时候选区”与“正式数据库”隔离（防污染）

绝对不能把实时录制的点直接写入主数据库。按照共识，拆开存。

**你的具体任务：**

- 维护两个容器：
  - **`SessionData`（内存临时）**：包含 `List<UUID> tempNodeIds` 和 `List<Segment> tempSegments`。玩家按 R 结束录制时，这里的 data 清空。
  - **`MasterDatabase`（持久化）**：包含全量的 `Map<UUID, Node>`、`Map<UUID, Segment>`、`Map<UUID, Road>`。
- **结束录制（按 R 停止时）**：
  - 将 `SessionData` 里的所有 `Segment` **尝试合并**到 `MasterDatabase`。
  - **合并逻辑**：遍历 `MasterDatabase` 的所有旧 Segment，运行**线段相交检测（叉积法）**。如果相交距离 < 2格，则把新段的端点坐标**吸附（Snap）**到旧节点的 UUID 上（消除手抖偏差），并自动将旧 Segment 在交点处一切为二。

### 阶段四：打通浏览器桥梁（极简第一步）

鉴于你说浏览器是最终编辑平台，现在**先别写 WebSocket 服务器**，太复杂了。先做最简导出。

**你的具体任务：**

1. 绑定一个 **`E`键（Export）**，仅在非录制状态下生效。
2. 按下 E 键，将 `MasterDatabase` 序列化为 **GeoJSON 格式** 的文件，存到 `.minecraft/config/你的模组名/roads_export.json`。
3. **GeoJSON 结构**：把每一个 `Segment` 的 `nodeIds` 还原成坐标数组，输出为 `LineString` 类型。同时把 `Road` 的名字写入 `properties` 里。

> 这一步做完，你就有了一个浏览器可以读取的静态文件。后续你用任何 Web 地图框架（Leaflet/MapLibre）加载这个 JSON，就立刻能看到你在游戏里录的全部道路，并可以在浏览器里“指指点点”规划编辑，之后再人工改 JSON 回导（先别做自动回导，手动替换文件即可）。
