```text
         ▲
=========
```

你很难知道：

* 这条路是不是和另一条路平行？
* 两条路是不是差了 2 格？
* 有没有形成一个完整环路？

因为你永远是第一人称。

但是浏览器：

```
+--------------------------+
|                          |
| ========                 |
|        \                 |
|         \                |
|          ========        |
|                          |
+--------------------------+
```

空间关系一下子就出来了。

所以我会建议职责划分成：

### 游戏端

负责：

> **采集（Capture）**

包括：

* 自动采样
* 候选节点
* 临时编辑
* 实时预览

---

### 浏览器

负责：

> **编辑（Edit）**

包括：

* Road 合并
* Segment 拆分
* 改名字
* 删除节点
* 属性编辑
* 搜索
* 导航
* 导出

也就是说：

**游戏里做 CAD 的采集。**

**浏览器做 GIS 的编辑。**

这样两边都会舒服很多。

## 2. Segment 的集合，其实就是 Road

你最后一句：

> 可以把路看成 segments 的集合

我完全同意。

甚至我觉得：

```text
Road
│
├── Segment1
├── Segment2
├── Segment3
└── Segment4
```

比 RoadName 更自然。

Road 不一定有名字。

例如：

```
Unnamed Farm Road
```

也是一条 Road。

Road 应该只是：

> 一个连续的、逻辑上的道路对象。

名字只是属性。

例如：

```java
class Road {

    UUID id;

    List<SegmentId> segments;

    String name;

    RoadType type;

}
```

RoadName 就不用单独存在了。

## 3. 我觉得最值得研究的是："什么时候生成 Candidate Node？"

这个我反而有一点不同意见。

你的文档现在比较偏：

> **几何检测**

例如：

* 转角
* 弦长
* 距离

但是我觉得对于 Minecraft 来说，**玩家的行为比几何更可靠。**

什么意思？

例如：

### 情况一

玩家一直骑马。

```
=====================
```

很稳定。

不用生成节点。

---

### 情况二

玩家突然减速。

```
=============
         ↓
```

为什么？

大概率：

* 在观察
* 在找路
* 到了路口

---

### 情况三

玩家停下来。

```
==========
       ●
```

停了 2 秒。

这是一个很强的信号。

---

### 情况四

玩家开始左右转头。

```
←
↑
→
```

说明：

他在看。

而不是赶路。

现实中：

> 人到了路口才会左右看。

---

所以我觉得 Candidate Node 的评分，可以来自多个因素。

例如：

```text
Score =

方向变化
+

速度变化

+

停留时间

+

视角变化

+

距离
```

而不是：

> 角度超过 15°

只有一个条件。

## 还有一个我突然想到、我觉得特别适合 Minecraft 的信号

你有没有注意到：

**Minecraft 玩家"拐弯"和"转头"是分开的。**

例如：

正常走路：

```
W
```

只是：

```
yaw
```

变化。

但是真正进入另一条路：

玩家通常会：

```
W+A

或者

W+D
```

也就是：

**移动向量发生了变化。**

而不是：

视角变化。

例如：

```
一直看北

但是

开始往西移动
```

这在 Minecraft 非常常见。

所以：

与其检测：

> yaw 变化

不如检测：

> **velocity（速度方向）变化**

甚至：

```text
Movement Vector

↓

Heading

↓

Heading Change
```

会比摄像机角度稳定得多。

## 我最后想提一个可能会影响整个架构的问题

你现在其实有两个完全不同的数据流：

```
玩家移动
      │
      ▼
 Candidate Nodes
      │
      ▼
 Segments
      │
      ▼
 Browser
```

但是浏览器其实也可以反过来：

```
Browser

↓

修改 Segment

↓

同步回游戏
```

如果以后你真的把浏览器做成主要编辑平台，我反而建议**游戏端不要直接维护"正式数据库"**。

游戏端只维护：

* 当前录制 Session
* 临时 Candidate
* 本地缓存

真正的 Road / Segment / Node 数据库，交给浏览器维护。

因为浏览器更适合做复杂编辑、撤销重做、拓扑校验、批量操作等功能。

这样整个系统会变成一种我很喜欢的模式：

> **Minecraft 是采集器（Survey Tool），浏览器是 GIS 工作台（Workbench）。**

我觉得这和你的定位——"给服务器制图员使用的辅助模组"——是高度一致的，而且未来扩展性会非常好。
